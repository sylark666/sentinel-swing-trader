System Architecture & Specification Document: Project Sentinel-Swing (v2.0)
1. Project Overview & Objective
Project Sentinel-Swing is a fully automated, cloud-native algorithmic swing trading system engineered for the NSE Nifty 500 universe. The system integrates with the Zerodha Kite Connect API for live execution, risk management, and data retrieval.
The primary objective is to execute rules-based swing trades (holding horizon: 2 to 15 days) with an absolute focus on deterministic execution, static network security, and structural protection against look-ahead bias and model overfitting.
Core Metrics & Targets
Target Profit: net profit per trade (fully netting out brokerage, STT, GST, exchange transaction charges, and slippage buffers).
Operating Window: Non-intraday, non-options. Equity cash segment only.
Model Execution Temperature: Hard-coded to 0 across all runtime environments and AI code-generation agents to guarantee strict mathematical logic.
2. Risk Matrix & System Constraints
The core architecture must programmatically enforce these rules at both the application state-machine layer and the database layer.
Capital Allocation Layer: Maximum capital allocation per trade is of total current account equity.
Concurrency Layer: Maximum of 3 concurrent open positions allowed simultaneously.
Execution Timing Constraint: No signal scanning or entry order generation may occur before 09:45 AM IST. This bypasses the heavy structural volatility, institutional order matching, and overnight gap pricing adjustments common during the market open ().
Order Co-dependency: Every entry order must immediately be accompanied by a co-dependent Target Limit order and a dynamic Trailing Stop-Loss Limit order.
Asset Rotation Logic: If the system has 3 active positions and discovers a higher-ranked signal during the 09:45 AM scan, it must evaluate if the alpha differential justifies liquidating the weakest current holding to rotate capital into the new asset.
3. Data Architecture & Multi-Timeframe Engine
To eliminate look-ahead bias and handle live intraday data streams safely, the system utilizes a split time-series database design.
Historical Data Layout
Granularity: Daily bars + 15-minute granular bars for the entire Nifty 500 universe.
Storage Engine: Local PostgreSQL with the TimescaleDB extension. Indexes must be explicitly built on (ticker_token, timestamp DESC).
The 09:45 AM Live-Candle Synthesis Engine
Because daily candles are incomplete at 09:45 AM, your signal script cannot use a standard historical daily bar lookup for the current day . The system must construct a Synthetic Daily Candle programmatically:
Fetch completed daily historical bars from Day backwards.
Query Zerodha's live market quote API via kite.quote("NSE:TICKER") at exactly 09:45 AM.
Extract the current day's open, high, low, and last_price.
Append this temporary synthetic candle to the historical array before passing it into your Python indicator script.
4. Operational & Infrastructure Security
Static IP Gateway Routing
Zerodha enforces a strict security mandate: All API order placements must originate from a registered Static IP address. Orders coming from dynamic cloud IP pools will be instantly rejected by the broker.
Architecture: Your cloud functions cannot hit Zerodha directly. You must deploy an AWS VPC (Virtual Private Cloud) or Google Cloud equivalent. Route all outbound Lambda execution traffic through a NAT Gateway bound to an Elastic IP (Static IP). This Elastic IP must be whitelisted in your Zerodha Developer Console.
Exchange-Compliant Order Routing (No SL-M)
CRITICAL EXCHANGE RULE: The NSE has discontinued Stop-Loss Market (SL-M) orders to protect against freak-trade slippages. All protective stops must use Stop-Loss Limit (SL) orders.
The Padded Execution Strategy: To prevent a fast price crash from blowing past a standard limit order without filling it, the execution module must calculate an Execution Protection Pad.
For a long trade with a trigger price at ₹100, the corresponding execution limit price must be hard-coded with a negative offset buffer (e.g., limit price set to ₹98). This ensures that when the exchange triggers the order at ₹100, it behaves like a market order down to ₹98, guaranteeing an immediate execution match in a falling book.
5. Quantitative Strategy Optimization
Volatility-Based Trailing Stop-Loss (ATR)
Instead of an arbitrary, rigid percentage trail (which suffocates low-beta stocks and exposes high-beta stocks to premature stops), the system must utilize a dynamic Average True Range (ATR) trailing mechanism:
Execution: Set the volatility multiplier () between via the backtest dashboard. To prevent execution whipsaws from intraday noise spikes, the calculation and tracking variables for shifting this trailing stop floor must execute strictly during the 03:25 PM IST position maintenance block.
Time-Series Purging Framework
When validating your Python signal scripts locally, standard K-Fold cross-validation invalidates results because swing trades hang open over multiple days, causing intense serial correlation across time frames.
The Fix: Implement Purged Cross-Validation in the backtester engine. When partitioning data, the simulator must programmatically drop (purge) all historical daily and 15-minute data bars spanning 15 days immediately following the boundary of any training data block. This eliminates data leakage and look-ahead bias completely.

7. System Panic & Safety Interventions
Autonomous Master Kill-Switch
To protect capital if cloud states drop completely out of alignment with the actual broker order book (e.g., database connection timeouts midway through order placement routines), the Telegram Bot interface must expose an immutable /panic endpoint.
Upon receiving the /panic command payload, the application must immediately bypass standard execution modules and prioritize this routine sequentially:
Purge Orders: Query kite.orders() and issue bulk cancellation requests for all pending GTT, Target Limit, and Stop-Loss Limit orders.
Flatten Inventory: Query kite.positions(), identify all open CNC equity holdings executed under the strategy framework, and convert them to immediate market-facing exit orders with aggressive limit padding to enforce a 100% cash position.
Freeze Engine: Hard-write a SYSTEM_LOCKED = True state boolean to the persistent cloud database, stripping AWS Lambda of its permission to process morning signals until a human operator conducts a structural post-mortem and manually resets the system flag.
